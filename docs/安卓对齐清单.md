## 二、系统能力边界（有意降级，不是没做）

| 项 | Android 做法 | iOS 只能这样 | 影响 |
|---|---|---|---|
| 后台用水监控 | 前台服务 `ShowerWatchService` 常驻轮询、超时自动关停 | 无前台服务；前台计时器 + 回前台 `reconcileOnResume` 对齐 | **App 被挂起/杀掉期间不会自动关阀**；回到前台会立刻补判断 |
| 常驻通知进度 | 通知栏每秒刷新计时 | 一条静态「使用中」通知 + 「结束用水」按钮 | 通知里看不到跳动的秒数 |
| 通知按钮直接关阀 | `PendingIntent` → 服务直接发请求 | 点按钮回前台再执行 | 多一步「打开 App」 |
| 桌面小组件 | `AppWidgetProvider` 三种尺寸 | WidgetKit（**暂不做**，按你的决定放到软件内完善之后） | — |
| 应用内更新 | 下载 APK + 调系统安装器 | 只做版本检测 + 更新日志 + 「看教程」跳 GitHub | 装包仍走侧载 |
| MAC 地址 | 蓝牙栈直接给 MAC | CoreBluetooth 只给 `CBPeripheral.identifier` | 改用「状态帧自报 MAC」+ manufacturerData 解析 |
| 系统「密码」自动填充 | Android Autofill | 需要 Associated Domains + AASA 文件 + 对应签名能力 | 目前只有应用内 Keychain 记住密码 |

## 六、2026-10-23 多设备第一阶段

- 参考 Android `utils/Notifier.kt` 的 `EXTRA_SNCODE` 和 `service/ShowerWatchService.kt` 的 `doFinish(snCode)`，通知操作按原设备和原订单处理，不使用当前页面的设备作为兜底。
- 云端通知停止前核对服务端订单；旧通知、不同账号、不同开始时间或订单号不匹配时拒绝操作。
- 恢复使用页只查询原订单：设备空闲、网络失败时不申请新费率；服务端订单变化时不覆盖原订单。
- 参考 Android 蓝牙控制器贯穿关阀与结算的方式，共用 BLE 会话加控制锁；设备状态帧核对 MAC 后才写关阀命令，关阀后重连、采集、上传、写回完成前不接入另一条控制链。
- 每笔结算捕获自己的时长与设备，延迟结算通知不删除新订单的使用中通知；监控任务增加身份复核，避免旧任务清掉新任务。
- 新增离线回归用例，覆盖通知身份、服务端订单变更、控制锁归属、恢复过程不触发开阀。完整界面和 BLE 行为仍需真机检查。

### 真机验收顺序

1. A、B 同时使用，停留 B 页面点击 A 的结束通知，确认仅 A 停止，B 卡片和计时保留。
2. A 结束后重新开启 A，点击旧通知，确认新订单不受影响。
3. 蓝牙 A 关阀结算过程中尝试开启 B，确认提示等待；A 结算完成后 B 能正常开启。
4. 杀掉 App 后从使用中卡片恢复；分别测试仍在用水、已经停止、断网，不应新增预扣订单。
5. 断开蓝牙后关阀，确认重连的是目标设备；查看导出日志中的设备编号、订单号与实际使用一致。

版本继续保持 3.1.0（18），软件更新的“看教程”功能不变。本阶段不新增后台常驻或 MQTT 实时消费能力。
